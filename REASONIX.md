# Stratum Backend

The backend is a **REST API**: JSON over HTTP, resource-oriented (`/api/v1/tickets`, `/api/v1/meetings/...`), using HTTP methods (`GET`/`POST`/`PUT`/`PATCH`/`DELETE`) and status codes to express semantics. **Standard-library-first**: no web frameworks, no ORMs.

**Stack:** Go 1.26+, `net/http` + `ServeMux` (stdlib), Postgres 16 via `database/sql` (stdlib) + `pgx` driver, OpenAPI 3.0 spec generated from the code (swaggo/swag) into `docs/`.

> Split out of the monorepo into its own repo (`stratum-api`).

---

## Folder Structure

Inspired by [golang-standards/project-layout](https://github.com/golang-standards/project-layout), trimmed to what this service actually needs. When in doubt, put code in `internal/`. Do not add layers until there is a real need.

```
backend/
├── cmd/
│   └── server/            # entrypoint: load config, open DB, wire store → service → handler → server
├── internal/
│   ├── config/            # config from environment variables (12-factor), fail fast on missing
│   ├── server/            # HTTP server: ServeMux routes, middleware wiring, startup/shutdown
│   ├── middleware/        # slog logging, auth (JWT), rate limiting, CORS, request ID, panic recovery
│   ├── handler/           # thin HTTP handlers: parse/validate → one service call → JSON response
│   ├── service/           # business logic / use cases (no HTTP, no SQL)
│   ├── store/             # Postgres access via database/sql; plain SQL, one file per aggregate
│   ├── model/             # domain types shared across layers
│   └── auth/              # JWT issuing/verification, RBAC rules (syndic / owner / tenant)
├── docs/                  # GENERATED by swaggo from code annotations — never hand-edit
├── migrations/            # versioned SQL files (up + down), e.g. 0001_create_users.up.sql
├── go.mod
└── Makefile
```

**Intentionally excluded** (kept out on purpose, don't add them back): `pkg/`, `web/`, `deployments/`, `scripts/`, `test/`, `configs/` — no public library API, no web assets, no external test utilities, env-only config. Tests live next to the code (`*_test.go`).

## Rules

### Standard library first
- Use stdlib: `net/http`, `encoding/json`, `log/slog`, `database/sql`, `errors`, `testing`.
- No web frameworks (no Gin / Echo / chi) and no ORMs (no GORM). `ServeMux` is enough: method-aware patterns (`GET /api/v1/tickets/{id}`), path values via `r.PathValue("id")`, middleware via wrapping handlers.
- Small, standard libraries are acceptable only where the stdlib has no answer: `pgx` (Postgres driver), `golang-jwt/jwt` (JWT). Nothing heavier — no query builders, no validation frameworks.

### Code-First (solo developer)
- The Go code is the **single source of truth** for the API — write handlers and DTOs by hand, in this repo (decided in ADR 002).
- Annotate handlers with swaggo comments; run `make api-docs` to regenerate `docs/` (`swagger.yaml`, OpenAPI 3.0). Generated output is never hand-edited.
- The frontend generates TS types from the generated spec (`openapi-typescript`); anything the frontend needs must be visible in the spec.
- REST conventions (below) are rules we follow, not a contract to validate against.

### Layers (keep them thin and strict)
- `handler`: parse and validate the request, call exactly one service method, map result/error to a JSON response. No business rules.
- `service`: business logic (voting, elections, finances, tickets). No HTTP, no SQL. Depends on `store` interfaces, not implementations.
- `store`: only `database/sql` + plain SQL against Postgres. Return domain errors (`store.ErrNotFound`) that services/handlers map.
- `model`: plain structs. Keep `json`/`db` concerns in the layer that owns them.

### REST API conventions
- All endpoints under `/api/v1/...` (versioned; bump the path segment on breaking changes).
- Resource-oriented paths, HTTP methods, meaningful status codes.
- Naming: kebab-case paths, camelCase JSON properties, PascalCase schema names.
- Auth: JWT Bearer security scheme; protected operations check it in middleware.

### API responses & errors
- Consistent JSON error envelope: `{"error": {"code": "...", "message": "..."}}`.
- Map store/service errors to proper HTTP statuses in the handler layer — never leak SQL errors or stack traces.

### Database
- Versioned SQL migrations in `migrations/`, applied in ascending order (`make db-migrate`), rollback via `make db-rollback`. Each migration is a pair: `NNNN_name.up.sql` + `NNNN_name.down.sql`.
- Table names: snake_case plural. Foreign keys: explicit, with meaningful names. (See root REASONIX.md.)

### Auth
- JWT in `Authorization: Bearer` header, verified in `middleware`.
- RBAC roles `syndic`, `owner`, `tenant`; put the current user + roles into the request context, enforce in handlers/services.

### Config
- Environment variables only (12-factor), parsed once in `internal/config` at startup; fail fast on missing required variables. No config files.

### Testing
- Stdlib `testing` only; table-driven tests.
- Handlers: `net/http/httptest` against the real `ServeMux`.
- Store: test against a real Postgres (docker-compose); no mocks unless genuinely needed.

### Tooling & hygiene
- `gofmt` on save (`gofmt -w .`), `go vet ./...`, `staticcheck ./...` for lint.
- Logging via `log/slog`; structured, request-scoped (request ID middleware).
- Conventional Commits (`feat:`, `fix:`, `chore:`, ...).

## Commands

```bash
go run ./cmd/server     # run the API
go test ./...           # run all tests
go build ./...          # build
go vet ./...            # vet
```

From the root Makefile: `make dev-backend` (hot-reload), `make api-docs` (regenerate `docs/` OpenAPI spec from code annotations), `make db-up` / `make db-migrate` / `make db-rollback`.
